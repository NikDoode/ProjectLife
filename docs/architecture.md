# Архитектура Project Life

## Назначение проекта

Project Life — таск-менеджер с несколькими представлениями одной и той же предметной модели.

Первая версия используется для проверки идеи: объекты должны храниться независимо от того, каким способом они отображаются пользователю.

Сейчас реализовано древовидное представление. Следующим основным представлением должна стать пространственная карта.

---

## Основная схема

```text
SQLite
    ↓
Предметная модель
    ↓
Проекция данных
    ↓
REST API
    ↓
Представление во frontend
    ↓
Inspector выбранного объекта
Текущая предметная модель

Основная сущность — Item.

Item может иметь один из типов:

area;
project;
task.

Основные поля:

id;
parent_id;
kind;
title;
description;
status;
priority;
due_at;
временные метки.

Связь parent_id формирует логическую иерархию объектов.

На текущем этапе области, проекты и задачи являются типами одной сущности, а не отдельными классами.

Основные архитектурные принципы
1. Предметная модель отделена от отображения

Item не должен знать:

где он расположен на экране;
каким компонентом он отображается;
открыт ли он в дереве;
выбран ли он пользователем.

Эти сведения относятся к интерфейсу или конкретному представлению.

2. Один объект может отображаться разными способами

Один и тот же Item может быть:

узлом дерева;
карточкой на пространственной карте;
строкой в другом представлении.

При этом идентичность объекта сохраняется: это не копии, а разные способы показать одну сущность.

3. Projection и View выполняют разные задачи

Projection преобразует предметные данные в структуру, удобную для конкретного отображения.

Пример:

плоский список Item
        ↓
TreeProjection
        ↓
вложенная структура children[]

View отображает результат проекции во frontend.

Пример:

TreeProjection
        ↓
TreeView
4. Выбор объекта является общим состоянием интерфейса

Выбранный объект не принадлежит конкретному представлению.

Объект может быть выбран в дереве или на будущей карте, после чего один общий Inspector показывает его свойства.

5. Пространственные координаты не принадлежат Item

Когда появится пространственная карта, положение карточки должно храниться отдельно от предметного объекта.

Координаты описывают размещение объекта в конкретном представлении, а не сам объект.

Текущий вертикальный срез

Сейчас система реализует следующий путь:

backend/data/task_manager.db
        ↓
SQLAlchemy Item
        ↓
CRUD
        ↓
TreeProjection
        ↓
GET /items/tree
        ↓
React TreeView
        ↓
выбор Item
        ↓
ItemDetails

Это первая работающая проекция предметной модели.

Backend

Текущая структура ответственности:

database.py — подключение к SQLite и управление сессиями;
models.py — SQLAlchemy-модели;
schemas.py — входные и выходные схемы API;
crud.py — базовые операции с хранилищем;
services/tree_projection.py — построение древовидной проекции;
api.py — HTTP-маршруты;
main.py — сборка FastAPI-приложения.

Backend не должен содержать сведения о визуальном оформлении компонентов.

Frontend

Frontend постепенно должен быть организован вокруг сменяемых представлений.

Ближайшая целевая структура:

frontend/src/
├── api/
├── components/
│   └── ItemDetails/
├── views/
│   └── Tree/
│       ├── TreeView.jsx
│       ├── TreeNode.jsx
│       └── Tree.css
├── App.jsx
├── App.css
├── index.css
└── main.jsx

views/ содержит конкретные механизмы отображения предметной модели.

components/ содержит общие части интерфейса, которые не принадлежат одной конкретной View.

Ближайшее направление развития
Выделить существующее дерево в TreeView.
Ввести выбор активного представления.
Сохранить общий Inspector.
Добавить простую пространственную View.
Хранить координаты объектов отдельно от Item.

На этом этапе не требуется заранее строить универсальную модель всех возможных сущностей и связей.

Архитектура должна расширяться по мере появления конкретной необходимости.

Инварианты проекта

При изменениях необходимо сохранять следующие правила:

Item не содержит координаты и состояние React-интерфейса.
View не владеет предметными объектами, а только отображает их.
Один Item может присутствовать в нескольких представлениях.
Inspector не должен зависеть от TreeView.
Новая функциональность не должна вводиться в рамках чистого рефакторинга.
Не следует заранее создавать абстракции, которые пока не используются.git status

# Основные принципы Project Life

## 1. Один объект — много представлений

Объект существует в модели только один раз.

Tree View, Spatial View, TodayPanel, Inspector и другие представления отображают один и тот же объект.

Копирование объектов между представлениями запрещено.

---

## 2. Представления независимы

Каждое представление решает свою задачу.

Оно не должно дублировать функции других представлений.

---

## 3. Простота

Предпочтение отдаётся простой архитектуре.

Если существует два решения с одинаковым результатом, выбирать более простое.

---

## 4. Минимальные изменения

Каждый этап должен вносить минимально необходимые изменения.

Избегать крупных рефакторингов без необходимости.

---

## 5. Совместимость

Новые функции не должны ломать существующее поведение приложения.
